## 대상 앱: 소심한 카공족 기록장

## 앱 기획 배경

카페 공부를 자주 하는데, (주문하고 너무 오래 있어서 그런지) 전날 갔던 카페를 또 가는 게 왠지 모르게 부담스러웠다. 사장님 눈치도 보이고, 그래서 전날 어디 갔는지만 외워두면 되는데, 까먹기도 하고 기록하기엔 너무 귀찮았다.

딱 이것만 하는 앱이 있으면 좋겠다고 생각했다. 오늘 갔던 카페 적고, 얼마 썼는지 기록하고, 어제 같은 데 갔으면 경고해주는 것. 단순하지만 나한테 실제로 필요한 기능이었다.

기술 스택은 HTML/CSS/JavaScript로만 제한했다. Gemini Canvas로 빠르게 프로토타이핑하면서 AI와 협업하는 방식도 같이 익혀보고 싶었다.

## 1. 초기 프롬프트

미션지에서 언급하고 있듯이, 처음부터 모든 걸 다 담으려고 하지 않았다. 이번 앱에서는 핵심 기능만 명확하게 전달하면서 코드 구조에 대한 방향은 내가 직접 잡아주기로 했다.

```
매일같이 집 앞에 카페에서 공부하는 소심한 카공족은 연속적인 날짜에 전날과 동일한 카페를 가는것은 상당히 부담스럽기 때문에,
연속적인 날짜에 같은 카페를 가는것은 싫어한다. 따라서 연속적인 카페를 피하기 위해서, 전날 갔던 카페를 작성해두는,
그리고 얼마나 해당 카페를 자주 다녔는지 체크하는 리스트를 만들려고 한다.

카페에 지출 또한 기록 가능하게 작성.
초성으로만 작성해도 알아서 풀 네임으로 작성하게끔 유도.
예를들어 "ㅁㄱ" 라고 입력하면 "메가" 이런식으로 작성해줘야함.

0. 타이틀: 소심한 카공족
1. 기술 스택: HTML, CSS, JavaScript만 사용할것. React나 다른 프레임워크는 사용하지 마.
2. 코드 스타일: OOP 원칙에 맞추어 코드 작성
3. 기본 베이직 카페리스트: "메가" "우지" "컴포즈" "스타벅스" "투썸" "이디야"
4. 무인카페의 경우 무인카페 라고만 기입.
```

이전에 몇 개 만들어 보았었는데, "OOP 원칙에 맞추어"라고만 썼을 때는 클래스 분리가 애매하게 나오는 걸 나중에 발견했다. 사실 첫 프롬프트에서 클래스 구조까지 명시했으면 더 좋았겠다는 생각은 있는데, 일단은 결과물 보고 판단하자는 입장이었다. 초기에는 과도하게 지시하기보다 Gemini가 어떻게 해석하는지 먼저 보는 것도 의미 있었다.

## 2. 프롬프트 반복 과정 (총 9회)

### 1차 — 기본 앱 생성

첫 결과물은 생각보다 빠르게 나왔다. 초성 변환, 카페 리스트, 지출 기록까지 기본 틀은 잡혔다. OOP 구조도 나름대로 잡혀있었다. 물론 클래스 분리가 내 의도와 완전히 일치하진 않았지만, 여기서 바로 리팩토링 요청을 하기보다 기능을 먼저 다 붙이고 나중에 정리하기로 했다. 지금 구조가 완전히 틀린 건 아니었으니까.

### 2차 — 전날 같은 카페 방문 시 경고 모달 추가

핵심 기능이다. 이 앱의 존재 이유라고 할 수 있는 "어제도 여기 갔잖아" 경고였다. 모달 형태로 띄워달라고 요청했다.

결과물은 얼핏 보면 잘 된 것 같았다. HTML에 모달 구조는 있었고, 트리거 로직도 있었다. 근데 실제로 입력해봤더니 모달이 뜨지 않았다.

원인을 직접 뜯어봤더니 두 가지 버그가 있었다.

**버그 1 — CSS transition 충돌**

`.modal-overlay`에 `display: none`과 `opacity: 0` + transition을 같이 쓰고 있었다. 이게 문제였다. `display: none` 상태에서는 요소가 렌더링 트리에서 아예 빠져나가기 때문에 브라우저가 transition을 계산할 시점이 없다. `display: none` → `display: flex`로 바뀌는 순간, opacity transition이 실행되어야 하는데, 브라우저 입장에서는 방금 생겨난 요소라 초기값부터 계산할 틈이 없다. 결국 opacity가 0에서 그대로 멈춰버렸다.

**버그 2 — 트리거 조건 누락**

모달 조건이 "전날 같은 카페"일 때만 잡혀있었다. 같은 날 같은 카페를 중복으로 입력하면 모달이 뜨지 않았다. 이건 로직 설계의 구멍이었다.

버그 원인을 파악했으니 원인과 수정 방향을 함께 써줬다.

```
다음 두 가지 버그를 수정해줘:

1. [CSS 버그] `.modal-overlay`에서 `display: none`과 `opacity transition`을 같이 쓰면
   브라우저가 transition을 실행하지 못해 모달이 보이지 않아.
   `display: none`을 제거하고, 대신 `visibility: hidden`과 `pointer-events: none`으로
   모달을 숨겨줘. `.modal-overlay.show`에는 `visibility: visible`과 `pointer-events: all`을
   추가해줘. `display: flex`는 base에 항상 유지해.

2. [조건 버그] 모달이 "전날 같은 카페"일 때만 트리거되는데,
   "같은 날 같은 카페를 중복 입력"할 때도 경고 모달이 뜨도록 조건을 추가해줘.
   (기존 연속 방문 경고는 유지)
```

이렇게 썼더니 훨씬 정확하게 수정됐다. "버그 고쳐줘"라고만 했을 때와 결과물의 질이 확연히 달랐다. 원인을 직접 분석해서 넘겨주면 Gemini가 엉뚱한 방향으로 고치는 일이 없었다. 그리고 이 과정이 나한테도 공부가 됐다고 생각한다. `display: none`과 transition의 관계는 직접 원인을 파고들면서 제대로 이해하게 됐다.

### 4차 — 이번 달 누적 지출 카드 추가

지출을 기록하기만 하고 합계를 볼 수 없으면 반쪽짜리기에 이번 달 총 지출을 카드 형태로 보여주는 기능을 추가했다.

여기서는 한번 메서드 이름을 미리 정해서 넘겨줘 보았다.

```
이번 달 누적 지출 금액을 표시하는 기능을 추가해줘.

요구사항:
1. "방문 기록" 섹션 위에 이번 달 누적 지출 카드를 추가해줘.
   표시 형식: "2월 총 지출: 23,500원" (현재 월 기준 자동 계산)
2. 새 기록이 추가될 때마다 금액이 실시간으로 갱신돼야 해.
3. CafeTracker 클래스에 getCurrentMonthTotal() 메서드를 추가해서
   entries 중 이번 달(YYYY-MM 기준)에 해당하는 항목의 cost 합산을 반환해줘.
4. UI는 기존 카드 스타일에 맞게 심플하게 디자인해줘. 지출이 0원이면 "아직 지출 없음"으로 표시해줘.
```

`getCurrentMonthTotal()`처럼 메서드 이름을 직접 지정해주는 게 효과적이라는 걸 이즈음에 파악했다. 이름을 안 주면 Gemini가 `calcMonthSpend()`나 `getThisMonthCost()` 같은 이름을 임의로 만드는데, 그러면 다음 프롬프트에서 메서드를 수정해달라고 할 때 컨텍스트를 다시 맞춰줘야 했다.

### 5차 — GitHub 잔디 스타일 방문 히트맵 추가

사실 이 기능은 처음부터 있던 계획은 아니었다. 기록을 쌓다 보니 시각적으로 한눈에 볼 수 있으면 좋겠다는 생각이 들었다. GitHub 잔디가 딱 떠올랐다. 날짜별 방문 빈도를 색상으로 보여주는 구조이다. 커피 테마로 색상을 잡았다.

```
방문 달력을 GitHub 잔디(contribution graph) 스타일로 한번 구현해줘.

[색상 - 커피 테마로]
- 0회(방문 없음): #EBEDF0
- 1회: #D6B896 / 2회: #B07940 / 3회 이상: var(--primary-color) #8B5A2B

[디테일]
- 셀에 마우스 호버 시 툴팁: "2월 14일 · 2회 방문"
- 요일 레이블(월/수/금만) 왼쪽에 표시 (깃허브 방식)
- 오늘 날짜 셀은 테두리 border: 2px solid var(--primary-color)
- 이번 달 범위 밖 날짜 셀은 렌더링하지 않음
```

색상도, 툴팁도, 요일 레이블 위치도 다 원하는 대로 나왔다. 근데 hover할 때 셀이 잘려 보이는 이상한 버그가 생겼다.

히트맵 hover 버그

셀에 마우스를 올리면 scale 애니메이션이 동작하는데, 셀이 컨테이너 경계에서 잘려 보였다.

원인은 `overflow-x: auto`였다. 스크롤을 위해 가로 overflow를 auto로 설정했는데, CSS 스펙상 `overflow-x`를 `auto`로 명시하면 암묵적으로 `overflow-y`도 `auto`가 된다. 결과적으로 scale된 셀이 y축으로 살짝 넘치는 순간 잘려버렸다. 직접 원인을 찾고나니 해결책이 바로 보였다.

### 6차 — 히트맵 hover 버그 수정

```
heatmap 셀 hover 버그를 수정해줘.

`.heatmap-container`의 `overflow-x: auto`를 제거하고,
바깥에 scroll wrapper div를 새로 감싸서 overflow-x: auto를 거기에 적용해줘.
heatmap-container 자체는 overflow: visible로 유지해.
```

scroll 영역과 overflow: visible이 필요한 영역을 div로 분리하는 것. 한 번에 정확하게 수정됐다. CSS 관련 버그는 특히 이렇게 해야 했다. 추상적으로 "hover가 이상해요!"라고 하면 Gemini가 CSS를 이것저것 만지다가 다른 부분을 건드리는 경우가 있었다.

### 7차 — 3일 연속 방문 시 특별 경고 모달

기능적으로 필요해서라기보다는 재미 요소로 추가했다. 3일 연속 같은 카페를 가면 "그러다 사장님이 알아보시겠어요"라는 메시지를 띄우는 것. 사소하지만 이런 디테일이 앱에 개성을 준다고 생각했다.

조건이 여러 개 겹칠 때 어떤 모달을 우선해서 띄울지가 중요했다. 명시하지 않으면 Gemini가 임의로 판단하거나, 최악의 경우 모달이 여러 개 동시에 뜰 수 있다.

```
기존 연속 방문 경고에 더해, 3일 연속 같은 카페 방문 시 별도의 재미있는 모달을 띄워줘.

[우선순위]
1순위: checkThreeDayStreak → "☕ 3일 연속 ${cafeName}이시네요...<br>그러다 사장님이 알아보시겠어요."
2순위: checkDuplicateVisit → 기존 모달
3순위: checkConsecutiveVisit → 기존 모달
(조건 하나만 걸리면 해당 모달 하나만 표시)

[기존 코드 변경 최소화]
새 메서드 추가와 handleFormSubmit 조건문 수정만 할 것.
CSS, UI 클래스, 모달 구조는 건드리지 말 것.
```

기존 코드 변경 최소화를 명시한 게 중요했다고 생각하는게, 이걸 안 쓰면 히트맵이나 모달 구조까지 손대서 멀쩡히 동작하던 기능이 갑자기 안 되는 경우가 생겼다.

그냥 추가 기능을 붙일 때는 항상 이 조건을 같이 넣기로 스스로 결정했다.

### 8차 — localStorage 연동

새로고침하면 데이터가 날아갔다. 당연한 문제였는데 생각보다 늦게 처리했다.

localStorage 연동을 요청할 때는 구체적으로 어느 클래스의 어느 시점에서 읽고 써야 하는지까지 명시했다.

```
앱을 새로고침해도 기록이 유지되도록 localStorage 연동을 추가해줘.

[CafeTracker 클래스 수정]
1. constructor에서 localStorage 불러오기 (키: 'cafe-tracker-entries')
   파싱 실패는 try-catch로 잡아 빈 배열로 fallback
2. addEntry() 메서드 끝에 저장 호출 추가
3. 별도 saveToStorage() / loadFromStorage() 메서드로 분리

[App 클래스 수정]
init()에서 로드된 데이터 기준으로 renderHistory, renderMonthlyTotal, renderHeatmap 초기 호출
```

try-catch fallback을 명시한 이유가 있다. localStorage에 손상된 데이터가 있으면 JSON.parse가 예외를 던진다.

### 9차 — 코드 품질 개선 3가지 묶음

기능 구현이 어느 정도 마무리되니까 코드를 다시 훑어보게 됐다. 쌓인 문제가 세 가지 보였다.

데드코드: `handleFormSubmit`에서 `showWarning()`이 한 번도 호출되지 않았다. 기능 추가 과정에서 더 이상 필요 없어진 메서드가 남아있던 것이다. 기능을 붙이다 보면 이전 버전 코드가 계속 남는다. 주기적으로 정리 프롬프트를 따로 날리는 게 필요하다.

조사 처리: "3일 연속 메가시네요"는 말이 안 된다. "메가이시네요"도 이상하다. 한국어 조사는 앞 글자에 받침이 있는지 없는지에 따라 달라진다. `getJosa()` 헬퍼 함수를 만들어서 처리해달라고 요청했다.

삭제 기능: 잘못 입력한 항목을 지울 방법이 없었다. id 기준으로 배열에서 제거하고 localStorage와 동기화하는 삭제 버튼이 필요했다.

```
세 가지를 수정해줘:

1. handleFormSubmit에서 showWarning()이 한 번도 호출되지 않아
   #warning-msg가 완전한 데드코드야. showWarning 메서드와 #warning-msg HTML/CSS를 전부 제거해줘.

2. 3일 연속 모달 메시지에서 카페 이름 뒤 조사를 자동으로 처리해줘.
   가능하다면 마지막 글자에 받침(종성)이 있으면 "이시네요", 없으면 "시네요"를 붙이는 getJosa(name) 헬퍼 함수를 추가해서 적용해줘.

3. 방문 기록 각 항목에 삭제 버튼(x)을 추가해줘.
   클릭 시 해당 entry를 entries 배열에서 id 기준으로 제거해. 그리고 localStorage 동기화 후 전체 화면을 갱신해줘.
```

독립적인 수정 세 개를 번호 매겨서 한 프롬프트에 묶었다. 컨텍스트가 유지되면서 각각 정확하게 반영됐다. 건별로 따로 날리는 것보다 이쪽이 더 효율적이었다.

### 잘 됐던 것들

1. 래스명/메서드명을 직접 지정하기

   `getCurrentMonthTotal()`, `checkThreeDayStreak()` 처럼 메서드 이름을 미리 정해서 넘겨줬다. 이름을 지정하지 않으면 Gemini가 임의로 네이밍해서 기존 구조와 맞지 않는 경우가 생겼다. 다음 프롬프트에서 그 메서드를 다시 언급해야 할 때 컨텍스트가 틀어지는 걸 방지할 수 있었다.

   게다가 이름을 지정해주면 그 의미까지 이해하는지, 더 의도한 바와 더 일치하게끔 코드를 작성한 듯한 느낌을 받았다.

2. 버그 원인 + 수정 방향을 쌍으로 제시하기

   "display: none과 opacity transition이 충돌해서 안 뜬다. 이렇게 고쳐라"처럼 원인과 방향을 묶어서 줬다. 이렇게 하면 엉뚱한 방향으로 고치는 빈도가 크게 줄었다. 그리고 버그 원인을 직접 파고드는 과정이 나한테도 학습이 됐다.

3. 우선순위 명시하기

   여러 조건이 겹칠 때 1순위 → 2순위 → 3순위 순서를 직접 지정했다. 중복 모달 같은 엣지케이스를 알아서 처리해줬다. 순서를 명시하지않으면 조건 판단을 Gemini가 임의로 해서 의도와 다른 동작이 나왔다.

4. 기존 코드 변경 최소화를 명시하기

   이 조건이 없으면 히트맵이나 모달 구조처럼 건드릴 필요 없는 부분까지 손대서 예상치 못한 버그가 생겼다. 기능을 추가하는 프롬프트에는 항상 이 조건을 붙이는 게 안전했다.

5. 독립적인 수정은 한 프롬프트에 번호 매겨서 묶기

   9차처럼 관련 없는 수정 세 개를 한 번에 요청했다. 컨텍스트가 유지되면서 각각 정확히 반영됐다.

6. 엣지케이스는 직접 명시하기

   try-catch fallback, 조건 우선순위, 타임존 이슈 같은 것들은 언급하지 않으면 처리되지 않는 경우가 많았다. 처음 몇 번은 말 안 해도 되겠지 싶었는데, 결국 직접 챙기는 게 빠르다는 걸 반복 경험으로 알게 되었다.

---

### 안 됐던 것들

CSS 디테일을 대충 요청하기

CSS는 구체적인 속성과 값까지 명시하지 않으면 잘 고쳐지지 않았다. `overflow-x: auto`를 wrapper로 빼야 한다고 정확히 말해줬을 때만 원하는 결과가 나왔다. "hover가 이상해요" 정도로는 부족했다.

이미지 경로 오류 감지

이미지 주소를 잘못 입력해도 Gemini가 오류가 아니라고 판단하는지 수정을 잘 하지 않았다. 경로 문제는 직접 확인하는 게 빠르다.

## 4. 배운 점

1. Gemini는 구조 설계보다 구현에 강하다고 느꼈다

   "OOP로 짜줘"라고만 하면 클래스 분리가 모호하게 나왔다. 클래스 역할과 메서드 이름을 미리 정해서 넘겨줬을 때 결과물의 완성도가 확연히 달랐다. AI가 판단하게 두는 게 아니라, 내가 설계를 잡고 AI가 구현을 채우는 방식이 잘 맞았다.

2. 버그는 다이렉트로 원인을 파악해서 넘기는 게 빠르다

   "모달이 안 떠요"라고만 하면 원인을 잘못 짚는 경우가 있었다. `display: none`과 CSS transition 충돌처럼 구체적인 원인까지 파악해서 수정 방향과 함께 줬을 때 한 번에 해결됐다. 직접 디버깅하는 게 귀찮아 보이지만, 원인을 알고 넘기면 반복 수정이 줄었다. 그리고 그 과정에서 나도 CSS 동작 원리를 제대로 이해하게 됐다.

3. 데드코드가 상당히 쌓인다. 기능을 추가하다 보면 이전 버전 코드가 남는다.

4. 엣지케이스는 직접 챙겨야 한다

   try-catch fallback, 조건 우선순위, 한국어 조사 같은 것들은 따로 말하지 않으면 누락됐다. AI가 알아서 처리해줄 거라는 기대를 줄이고, 내가 생각해둔 엣지케이스를 프롬프트에 명시하는 습관이 결국 더 빠른 결과로 이어졌다고 생각한다.
---

## 5. 리뷰어에게 피드백 받고 싶은 포인트

CSS 버그 프롬프팅 방법

Gemini Canvas를 쓰면서 다른 것 보다 CSS 관련 버그가 유독 많이 생겼습니다. `display: none` + `opacity transition` 충돌처럼, (이런 대 ai 시대에) 결국엔 내가 직접 이슈를 파악해서 프롬프트에 명시해야 수정이 되고 그냥 반복해서 보이는 부분을 표현해서 설명하면 잘 이해를 못하는 듯한 느낌을 받았습니다. AI로 CSS 작업을 할 때 이런 디버깅 루프를 줄이기 위한 프롬프팅 방법이 있다면 꼭 듣고 싶습니다.
