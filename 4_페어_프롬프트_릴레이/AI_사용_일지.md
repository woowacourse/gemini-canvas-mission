### 대상 앱 이름: 눈 건강 지킴이

### 1. 초기 프롬프트

개발자들이 코딩을 할 때 눈을 오래 뜨고 있으면 아프잖아. 그래서 그걸 방지하기 위해서 웹캠을 활용해서 눈깜빡임 횟수나 눈 건강 상태를 체크해주고 눈을 깜빡이지 않으면 알림을 주는 그런 웹앱이 있었으면 좋겠어.
javascript, html, css만 사용하고 react와 같은 다른 프레임워크는 사용하지 않았으면 좋겠어.

### 2. 프롬프트 개선 과정

- 처음 결과물의 문제점은 무엇이었나요?

  최초 설계된 Canvas의 코드에는 필수적인 기능(눈 깜빡임 인식, 타이머)은 있었으나, 실제 사용 환경에서 발생하는 다양한 예외 상황을 처리하지 못하는 문제점들이 있었습니다.

    - **예외 처리 부재**: 자리 비움 등으로 얼굴이 인식되지 않을 때도 타이머가 작동하여 허공에 알람이 울렸습니다.

    - **기능 오작동**: 카메라 화면 숨기기 버튼을 눌러도 캔버스 뒤의 원본 비디오가 그대로 투과되어 보이는 버그가 있었습니다.

    - **통계 불안정성**: '분당 깜빡임 횟수(BPM)' 기능 추가 후, 측정 초기 1~2초 만에 한두 번 깜빡인 것을 1분 비율로 뻥튀기하여 80회 이상으로 잘못 계산하는 불안정한 로직이 있었습니다.

    - **의도치 않은 알람**: 사용자가 피곤해서 눈을 감고 휴식하려 할 때, 이를 '장시간 깜빡이지 않음'으로 인식해 경고음을 발생시켰습니다.

    - **데이터 초기화 누락**: 카메라 밖으로 나갔다 돌아와도 이전 세션의 '총 깜빡임 횟수'가 리셋되지 않고 계속 누적되었습니다.

- 어떤 식으로 프롬프트를 수정했나요?

  단순히 "고쳐줘"가 아니라 실제 테스트하며 겪은 구체적인 상황과 불편함을 묘사하고, 새로운 아이디어를 제안하는 방식으로 프롬프트를 작성했습니다.

    - **버그 제보**: "카메라 화면 표시 기능을 껐을 때는 카메라 화면이 보이지 않게 해줬으면 좋겠어."

    - **구체적 조건 제시**: "눈이 인식되지 않았을 때 마지막 깜빡임 후 기능을 실행하지 말아줘.", "얼굴 인식 대기중 상태가 되면 총 깜빡임 횟수를 0회부터 다시 카운트 하는 것으로 변경해줘."

    - **원인 분석 및 아이디어 제안**: "휴식하려고 눈을 감고 있었는데 알람이 떠. 근데 이걸 잘 활용하면 졸음방지에도 좋을 것 같은데 어떻게 처리할까? 계산이 80을 찍었어."

    - **디테일/감성 추가**: "권장 횟수 기준(15회) 맞춰줘", "다크모드 추가해줘", "귀여운 눈물방울 캐릭터 만들어줘", "무표정 이모지로 바꿔줘" 등 UI/UX 디테일을 하나씩 덧붙여 나갔습니다.

- 몇 번의 반복을 거쳤나요?

  16회의 반복을 거쳤습니다.

### 3. 효과적이었던 프롬프팅 전략

- 어떤 방식으로 요청했을 때 원하는 결과가 나왔나요?

    1. 단순한 버그 제보가 아닌, 맥락과 증상을 구체적으로 묘사하기

       "분당 환산 계산이 이상해"라고만 하지 않고, "지금 해보니까 거의 80을 찍어버렸어. 원래 10~20정도가 정상 아니야?"라고 구체적인 수치와 기대하는 정상 상태를 비교해서 설명했습니다.

       > 이를 통해, AI가 원인(초기 1~2초의 데이터를 1분으로 뻥튀기하는 로직 오류)을 정확히 진단하고, 15초의 대기 시간을 두는 측정 안정화 로직을 스스로 설계하도록 유도할 수 있었습니다.

    2. 발생한 문제를 새로운 기능으로 연결하여 제안하기

       "휴식하려고 눈을 감고 있었는데 알람이 떠. 근데 이걸 잘 활용하면 졸음방지에도 좋을 것 같긴 한데 어떻게 처리할까?"

       > 이를 통해, 단순한 오류 수정을 넘어 AI가 기존의 문제점을 역발상하여 졸음 감지 시 더 높은 주파수의 경고음과 보라색 화면을 띄우는 훌륭한 신규 기능으로 발전시켜 주었습니다.

    3. 명확한 제약 조건 설정하기

       처음부터 "javascript, html, css만 사용하고 react 같은 프레임워크는 쓰지 말아줘"라고 한계선을 명확히 했습니다.

       > 이를 통해, 별도의 복잡한 설치나 빌드 과정 없이 브라우저에서 즉시 실행 가능한 단일 파일 형태의 가벼운 웹앱 코드를 얻어낼 수 있었습니다.

- 반대로 효과가 없었던 방식은 어떤게 있었나요?

    1. 문제 현상만 전달하기

       "일단 카메라 화면 표시 기능이 있는데 제대로 작동을 안 해."와 같이 어떤 것이 문제인지 정확히 파악할 수 없도록 전달하여 어떤 식으로 기능이 작동하지 않는 것인지에 대한 설명이 부족해서 제대로
       수정하지 못했습니다.

       하지만 이후 "카메라 화면 표시 기능을 껐을 때는 카메라 화면이 보이지 않게 해줬으면 좋겠어."와 같이 구체적으로 기대하는 결과를 덧붙여서 원활하게 수정할 수 있었습니다.

       문제 현상과 기대 결과를 함께 묘사하는 것이 중요함을 깨달았습니다.

    2. 모호하거나 주관적인 기준으로 요청하기

       "권장 분당 깜박임 횟수에 충족하는지. 그런 것도 좀 있으면 좋겠어. 지금처럼 '눈 상태 양호' 이것도 기준을 좀 잘 써줬으면 좋겠어."와 같이 구체적인 기준이 아닌 추상적으로 요구하여 제대로 반영되지
       않았습니다.

       하지만 이후, "눈 깜빡임 권장횟수는 1분 15회 이상부터인데 수정해줄래?"와 같이 명확한 기준을 잡아주어 명확한 기준을 통해 판단할 수 있도록 하였습니다.

### 4. 배운 점

- Gemini Canvas를 효과적으로 사용하기 위한 나만의 팁이 있다면?
    - **웬만하면 Pro 모드를 활용하자.**

      빠른 모드와 사고 모드는 Pro 모드보다는 속도가 빠르지만 완성도가 많이 떨어진다. Pro 모드를 사용해야 추가적인 수고를 덜게 된다.
    - **한번에 너무 많은 요구사항을 요청하지말자.**

      한번에 너무 많은 요구사항을 요청할 경우, 과부하가 걸려서 렉이 걸리는 경우가 많았다. 한 프롬프트에 1~2개 정도의 요구사항을 작성해야 좋다.

    - **완성된 기능들에 대해 더이상 해당 기능을 건드리지 못하도록 프롬프트에 명확하게 남기자.**

      ex) 00기능은 완성됐으니까 해당 기능은 이제 건드리지마.

    - **오류를 수정할 때는 현재 나타나는 오류 증상과 기대하는 정상적인 결과를 비교해서 알려주자.**

      "계산이 이상해", "제대로 작동 안 해"라고 모호하게 말하기보다는, "지금 80이 나오는데, 정상이라면 10~20이 나와야 해"처럼 구체적인 수치나 상황을 짚어주면 AI가 로직의 잘못된 점을 훨씬 빠르고
      정확하게 찾아내어 수정해 준다.

    - **단순한 버그 수정을 넘어 새로운 기능으로 역제안하며 AI와 브레인스토밍하자**

      눈을 감고 눈을 쉬고 있었을 때, 의도치 않게 알람이 울리는 것을 발견했을 때 이를 단순히 수정하는 것에 그치지 않고 "이걸 졸음 방지 기능으로 활용하면 어떨까?"라고 질문을 던져서 생각하지 못했던 추가
      기능을 덧붙일 수 있었다.
