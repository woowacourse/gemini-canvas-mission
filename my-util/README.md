### 이 앱을 만든 이유
- 어떤 문제/불편함을 해결하려고 했나요?
> 우테코 생활하다 보면 회고를 숙제처럼 하게 되는 경우가 있습니다.  
> 진행한 일들만 쭈욱 나열하는 '나열식 회고'는 성장에 아무런 도움이 안 됩니다.
> 특히 기술적인 선택을 할 때 내가 왜 이 길을 택했는지, 혹시 편한 길로 도망친 건 아닌지 스스로 점검하기가 너무 어렵습니다.
> 
> 또한, 기술적인 선택을 할 때 논리적 근거 없이 익숙한 방법을 택하고도,  
> 회고 시에는 이를 '최선'이었다고 합리화하며 넘어가는 안일함을 경계해야 합니다.
>
> '정신체리'는 바로 그 안일함을 찾아내기 위해 만들었습니다.

- 이 앱을 언제, 어떻게 사용할 건가요?
> 스스로의 의사결정 과정에 치열한 고민이 부족했다고 느껴질 때 사용합니다.  
> 데일리 회고 초안을 붙여 넣으면, 시니어 코치 페르소나의 AI가 당신이 나열한 기술 용어 뒤에 숨겨진 안일함에 대해 분석합니다.
> 
> 비평을 통해 자신의 안일한 태도를 직면하고,  
> 이어지는 심층 질문에 답하며 왜 그 기술인가, 기회비용은 무엇인가를 깊게 파고들어 진짜 성찰이 담긴 리포트를 완성합니다.

<br/><br/>

### 주요 기능

**의사결정 및 타협 지점 분석**
> 회고록의 문장을 분석하여 성찰이 담긴 문장과 단순히 사실만 나열된 문장을 구분합니다.  
> 특히 논리적 근거 없이 타협한 것으로 의심되는 지점을 '비평 포인트'로 짚어냅니다.

**냉철한 성찰 비평**
> 시니어 개발자의 관점에서 작성자의 안일함을 지적합니다.  
> 감성적인 위로보다는 "왜 그런 선택을 했는지", "정말 원리를 이해하고 쓴 것인지"에 대해 날카로운 피드백을 제공합니다.

**5단계 직면 인터뷰**
> 비평을 바탕으로 작성자의 사고를 파고드는 5가지 질문을 던집니다.  
> 지식 확인이 아닌 '도전 의식'과 '장악력'을 묻는 질문을 통해 회고의 깊이를 강제로 확장합니다.

**최종 성찰 리포트**
> 대화 내용을 종합하여 [핵심 깨달음 / 도전 의식 / 향후 개선 방향]을 개괄식으로 정리합니다.  
> 포장된 회고가 아닌, 다음 단계에서 실천해야 할 구체적인 전략을 도출합니다.

<br/>

### AI 기능
**Gemini 2.5 Flash**
- > 문장 단위의 단순 패턴 매칭이 아니라 글 전체의 맥락을 파악하여 '개발자로서 더 고민했어야 할 지점'을 찾아냅니다.

**구조화된 데이터 추출**
> 사용자의 입력을 분석하여 JSON 형식으로 변환, UI 요소(하이라이트 색상, 게이지 점수 등)와 연동하여 시각적인 피드백을 제공합니다.

## AI 사용 일지

### 1. 초기 프롬프트
```text
제목: 우테코 8기 회고 굴착기 - "Fact to Challenge Driller"

1. 앱의 목적 및 페르소나

목적: '오늘 무엇을 했다'라는 단순 사실(Fact) 나열 위주의 회고를 분석하여, 그 이면에 숨겨진 '왜(Why)'와 '어떻게(How)'를 끌어내고 도전 의식을 고취함.

페르소나: 부드러운 위로보다 날카로운 통찰을 선호하는 우테코 시니어 코치. 사용자가 안일하게 작성한 문장을 귀신같이 찾아내어 뒤통수를 때리는 질문을 던짐.



2. 핵심 기능 로직 (JavaScript)

[Sentence Classifier]: 입력된 텍스트를 문장 단위로 분리하고, 정규표현식을 사용하여 다음 두 가지로 분류함.

Fact(사실): "~했다", "~구현했다", "~배웠다", "~사용했다"로 끝나는 단순 나열형 문장.

Insight(통찰): "~라고 생각했다", "~때문에 고민했다", "트레이드오프", "실패했다", "의문이 들었다" 등 사고의 과정이 포함된 문장.

[Comfort Zone Score]: (Insight 문장 수 / 전체 문장 수) * 100 점수를 계산하여 시각화. 40점 미만일 경우 "안일함 경보" 발령.

[The Drilling Engine]: Fact로 분류된 문장 중 하나를 랜덤하게 선택하거나 사용자가 클릭하면, 해당 문장의 키워드를 기반으로 3단계 심층 질문 생성:

1단계 (기술적 근거): "그 기술을 선택한 게 최선이었나? 단순히 익숙해서 선택한 것 아닌가?"

2단계 (트레이드 오프): "그 선택으로 인해 포기해야 했던 가치는 무엇인가? (예: 시간, 성능, 가독성 등)"

3단계 (확장성 및 도전): "만약 요구사항이 10배 까다로워진다면, 지금 네가 한 방식은 무용지물이 되지 않을까? 어떻게 대비할래?"



3. UI/UX 구성 (HTML/CSS)

Layout: 좌우 2분할 대시보드.

좌측 (Input Zone): 회고록 원본을 붙여넣는 넓은 텍스트 영역.

우측 (Analysis Zone): 실시간 분석 결과(Fact vs Insight 비율)와 앱이 던지는 '공격적인 질문'이 나타나는 영역.

Visual Effect:

단순 Fact 문장에는 빨간색 밑줄(Wave underline) 표시.

Insight 문장에는 청록색 형광펜 효과 표시.

질문이 나타날 때 화면이 미세하게 흔들리는(Shake) 효과로 '뒤통수 타격'을 시각화.

Gauge: 상단에 '사고의 깊이(Thinking Depth)' 게이지를 두어, 질문에 답변할수록 게이지가 차오르게 함.



4. 최종 결과물 생성

모든 질문에 답변하면, [기존 사실 + 추가된 고민 + 내일의 도전 과제]를 조합하여 **"진짜 성찰이 담긴 우테코식 회고록"**을 마크다운 형식으로 자동 생성하고 복사 버튼 제공.



5. 기술 제약 및 문구

제약: 외부 라이브러리 없이 순수 HTML/CSS/JS로 작성할 것.

필수 포함 문구: "안일함은 성장의 적입니다.", "사실 나열은 일기장에나 하세요.", "진짜 도전을 기록할 준비가 되었나요?"

이 요구사항을 바탕으로 즉시 실행 가능한 index.html 코드를 작성해줘.
```

### 2. 프롬프트 개선 과정

#### 문제점
> 초기에는 정규표현식 기반으로 "~했다"를 찾았으나, "셔틀을 탔다"와 같은 정말 일반적인 사실 기술과 "Redux를 썼다" 와 같은 개발 사실 기술을 구분하지 못해 기술적 근거가 필요 없는 일상 문장에도 비평이 가해지는 문제가 있었습니다.

#### 수정 방향
> 문장 단위 분류 로직을 Gemini AI를 연동하여 '기술적 사실'과 '일반적 사실'을 구분하도록 프롬프트를 고도화했습니다.

#### 반복 횟수
> UI 레이아웃 변경(사이드바 -> 가로형 -> 전체 뷰 전환), 테마 변경(다크모드 -> 우드 톤), 로직 수정 등 약 10회 이상의 반복을 거쳐 완성되었습니다.

<br/>

### 3-1. 효과적이었던 프롬프팅 전략

**페르소나 부여**
> '독설가 시니어 코치', '정신체리'와 같은 구체적인 캐릭터를 부여했을 때 응답의 톤앤매너가 일관되고 흥미롭게 유지되었습니다.

**JSON 스키마 정의**
> AI에게 응답을 요구할 때 명확한 JSON 구조를 지정하여 앱의 UI와 로직이 깨지지 않고 안정적으로 통신하게 했습니다.

**비동기 뷰 전환**
> "분석 버튼 입력 시 인풋창을 숨겨라"와 같이 상태에 따른 UI 변화를 구체적으로 요청하여 사용자 경험을 직관적으로 만들었습니다.

### 3-2. 효과적이지 못했던 프롬프팅 전략
**검증 불가능한 '모호한 성공 기준'**
> 바이브 코딩을 하다보니 안일하게 생각했던 나머지 "제대로 동작하게 해줘"라는 추상적인 믿음에 의존하여 기능 구현을 진행했고,
> 모든 기능 개발 후 기능 별 '검증 루틴'이 부족했습니다.
> TDD 의 부재가 바이브코딩의 단점이 될 수 있다는 점도 깨달았습니다...
> 
> 알림이 뜨지 않아도 AI는 코드를 다 짰다고 보고했고, 저 역시 성공 기준을 명확히 세우지 않아 리뷰어의 지적 전까지 오류를 인지하지 못했습니다.
> 
> "10자 미만 입력 후 버튼 클릭 시 특정 메시지가 화면에 노출되는가?"와 같이 테스트가 가능한 형태의 성공 기준을 프롬프트에 포함해야 안정성을 높일 수 있을 것 같습니다.

### 4. 배운 점
**단계적 빌드업 프롬프트 활용하기**
> 가장 마지막으로 개발한 앱인 `easy-k8s` 은 기존 앱을 만들 때 사용한 프롬포트와 다르게 전체 요구사항을 5단계로 나누어 요청했습니다.
> 
> 처음엔 서비스명, 디자인, 바닐라JS 조건부터 주고, 이후에 `접속 흐름`, `자기 치유`, `오토스케일링`의 기능을 순차적으로 요청하고, 마지막으로 퀴즈를 만들어달라는 요청을 했습니다.
> 
> 그 결과 한 번에 너무 많은 컨텍스트를 주어 발생할 수 있는 코드 누락이나 로직 충돌이 거의 발생하지 않았고,  
> 각 단계에서 동작을 즉시 확인할 수 있어 디버깅 시간을 다른 앱에 비해 절반 이상 줄었던 것 같습니다.

**구체적인 지시어로 요청하기**

> 단순히 “이런 기능 만들어줘”와 같은 모호한 요청을 통해 만들어진 결과물은 오히려 여러 차례의 버그 해결 과정에서 역설적으로 버그가 증식한다는 것을 깨달았습니다.
> 
> 처음부터 성공 조건을 수치를 활용한 언어로 구체화하여 전달하는 것이 여러 차례의 디버깅보다 훨씬 효율적이고 버그 발생률도 적었습니다.  
> AI 를 활용할 수 있는 개발자라면, AI에게 정확한 의도와 방향을 전달하는 번역가의 역할로도 살아남을 수 있겠다는 생각도 들었습니다.

**두려움 없는 시도가 가능해졌다!**

> AI 와 협업하여 앱을 만드는 기술이 상상했던 것 보다 많이 발전되어 있었습니다.  
> 복잡한 로직 이라도 일단 실행해 볼 수 있는 용기를 얻은 것 같습니다.
> 
> 이전에는 AI api 를 연동하여 질문을 생성하는 기능만 해도 구현하려면 설계 단계에서부터 높은 진입장벽을 느꼈을 것입니다.  
> 하지만 이제는 아이디어를 즉시 코드로 구현해보고 실패하면 프롬프트를 수정하며 다시 도전하는 과정을 빠르게 반복할 수 있게 되었습니다.

### 5. 리뷰어에게 피드백 받고 싶은 포인트
