# AI 사용 일지 — 페어 프롬프트 릴레이

## 대상 앱: AI 세계 여행 다트

---

## 페어 릴레이 방식이란

애니 크루와, 윤돌 크루와 함께 진행하였다.

이번 앱은 셋이서 번갈아가며 Gemini Canvas에 프롬프트를 날리는 방식이었다. 한 사람이 프롬프트를 쓰면 결과물이 나오고, 다음 사람이 그 결과물을 보고 다음 프롬프트를 쓰는 식의 릴레이다.

하다 보니까 상당히 흥미로운 점이 있었다. 혼자 할 때보다 다음 단계를 예측하기 어렵다는 것, 각자 프롬프트 스타일이 다르다는 것, 그리고 다른 크루원들마다 아이디어가 모이다 보니 상당히 빠른 시간에 완성도 있는 앱을 만들었다는 것.

---

## 앱 기획 배경

오늘 데일리 미팅 아이스브레이킹 주제가 여행이었다. "본인의 인생 여행지가 있으신가요?"

그게 이 앱의 시작이었다. 이 앱은 지구본을 돌려서 아무 데나 찍으면, 거기가 어딘지 AI가 알려주고 추천 명소까지 뽑아주는 앱이다. 다트처럼 던지는 느낌이 콘셉트였다.

개인적으로는 3D 지구본을 직접 만들어보는 게 처음이었다. 다른 두 크루 팀원분들은 알고있었지만 나는 Three.js를 직접 써본 적도 없었고(페어 크루가 설명해주었다), 좌표 계산이 얼마나 복잡한지도 몰랐다. 그냥 재밌어 보여서 선택한 주제였는데, 실제로 만들어보니까 생각보다 깊은 곳에서 문제가 터졌다. 그게 이번 일지의 핵심이 되기도 했다.

---

## 프롬프트 릴레이 전체 흐름 (총 11회)

### 1회 — 초기 프롬프트 (앱 생성)

```
여행지를 정하는 웹앱 서비스를 만들고 싶다.

기본형태가 지구본(위성형태)이 매우 빠르게 회전상태

클릭을 하면 클릭한 위치에 포인트가 남는다 (다트 형식도 가능)

그 포인트를 서서히 3초 뒤에 확대되면서 자세한 정보 및 관람을 추천하는 형태를 가짐

단, "HTML, CSS, JavaScript만 사용해서 만들어줘. React나 다른 프레임워크는 사용하지 마."
```

Gemini는 Three.js를 바로 끌어들였다. 순수 JS만 쓴다고 했지만 Three.js는 라이브러리라 통과된 것이다. 위성 텍스처, 3D 핀, 카메라 줌인, Gemini API 연동까지 한 번에 나왔다. 첫 결과물치고는 꽤 완성도가 있었다.

---

### 3회 — 경도 오차 발생, 원인 질문

```
경도가 특정 수치만큼 실제 좌표값이랑 내가 찍은 포인트 지점이랑 차이가 나는것 같다.

왜 나는거 같아?
```

단순히 "고쳐줘"가 아니라 "왜 나는 거야?"라고 먼저 물어본 것이 이번 릴레이에서 가장 좋은 판단이었다. 원인도 모르고 수정만 요청하면 엉뚱한 데를 건드리게 된다는 걸 직전 프로젝트에서 이미 배웠다.

Gemini의 설명은 이랬다. Three.js의 `SphereGeometry`에 텍스처 이미지가 입혀지는 기준점(UV Mapping)과 `Math.atan2` 함수의 기준축이 일치하지 않는다는 것이다. 세계지도 이미지는 중앙이 경도 0도(본초 자오선)인데, Three.js 구체는 다른 축을 기준으로 이미지를 감싸기 시작한다. 그래서 90도에서 180도 정도의 오프셋이 생긴다고 했다.

원인을 들으니 납득이 됐다. 코드를 수정해달라고 요청했다.

---

### 4회 — Gemini의 1차 수정 시도, 여전히 틀림

Gemini가 내놓은 수정 코드는 다음과 같았다.

```javascript
let lon = Math.atan2(vec.z, -vec.x) * 180 / Math.PI;
```

직접 찍어보니까 여전히 맞지 않았다. 구체적인 수치로 확인해봤다.

```
내가 찍은 곳은 -33.043154, 148.818657 부근인데 앱에서는 -29.8653, 57.1677 이라고 나와. 완전 차이나는데?
```

위도는 그나마 비슷했는데 경도는 91도 가까이 차이가 났다. Gemini가 "기준점을 보정했다"고 했는데, 보정 방향이 틀린 것이었다.

---

### 5회 — 아크탄젠트

여기서 잠깐 멈추고 직접 생각해봤다. `Math.atan2(vec.z, -vec.x)`에서 `-`를 쓰는 게 맞는지 의심이 들었다. atan2의 인자 순서는 `atan2(y, x)`인데, Three.js의 좌표계에서 경도를 어떤 축으로 나타내는지 생각해봐야 한다.

구체 위의 한 점을 (x, y, z)로 나타낼 때, 경도는 xz 평면에서의 각도다. y는 위도를 담당하고, x와 z가 경도를 결정한다. 기본 좌표계에서 z축이 화면 앞쪽을 향하고 x축이 오른쪽이라는 걸 생각하면, 텍스처가 어디서 시작하는지에 따라 부호와 인자 순서가 달라진다.

`atan2(vec.z, -vec.x)` 대신 부호를 바꿔서 `atan2(-vec.z, vec.x)`를 써보면 어떨까 싶었다.

```javascript
let lon = Math.atan2(-vec.z, vec.x) * 180 / Math.PI;
```

직접 바꿔봤더니 좌표가 정확하게 맞아떨어졌다. Gemini에게 그냥 다이렉트로 이 수정을 그대로 적용해달라고 요청했다.

```
let lon = Math.atan2(vec.z, -vec.x) * 180 / Math.PI;

이거

let lon = Math.atan2(-vec.z, vec.x) * 180 / Math.PI;

이걸로 수정 해봐.
```

내가 수학까지 공부할 줄이야. 그런데 정작 중요한 것은, Gemini는 원인을 설명하진 못하고 그냥 반영했다. 수학적으로 두 식이 어떻게 다른지, 왜 한쪽이 맞고 다른 쪽이 틀린지는 Gemini도 정확히 설명하지 못했다. 

이 순간이 이번 릴레이에서 가장 기억에 남는 부분이다. AI가 원인은 맞게 설명했는데 수정 방향은 틀렸고, 결국 직접 축의 부호를 바꿔가며 실험해서 답을 찾았다.

---

### 6회 — 장소 이미지 추가

```
해당 좌표를 찍고 나서 장소 정보를 추천해줄 때, 해당 장소의 이미지 1장도 함께 추가해줘.
```

Gemini는 Imagen 4.0을 연동해서 장소 이름 기반으로 이미지를 실시간 생성하는 방식을 제안했다. 나름 진짜같다. 결과물에 생동감이 생겼다.

---

### 7회 — 지구본 크기 80%로 축소

```
지구본 사이즈를 현재 사이즈에서 80% 사이즈로 줄여줘 (위 아래가 잘리고 있음)
```

반지름이 화면 높이를 넘어서 위아래가 잘렸다. 100에서 80으로 줄이면서 카메라 줌인 거리, 핀 위치 계산까지 같이 조정됐다. 단순한 수치 변경인데 연쇄적으로 건드려야 할 게 많았다.

---

### 8회 — 회전 속도 스테퍼 추가

```
회전속도를 조절할 수 있는 stepper를 넣고, 값이 변하면 그 즉시 적용되게 해줘.
x0.5 ~ x2 까지의 범위로 만들어줘. 현재 속도가 x1이야. 0.1씩 변하게 해줘.
```

지구본이 너무 빨리 돌면 원하는 지점을 클릭하기 어렵다. 속도를 직접 조절할 수 있으면 정밀하게 다트를 던질 수 있다. `rotationSpeed` 변수를 실시간으로 바꿔서 즉시 반영되게 만들었다.

---

### 9회 — 카메라 시점 옵션 추가

```
카메라 위치를 북반구 또는 적도, 또는 남반구로 향하는 옵션을 만들어줘.
기본값은 적도야. 옵션을 선택하는 즉시 적용해줘.
```
페어가 된 한 크루는 8번째 시도와 마찬가지로 항상 기본값을 제안했었는데, 이 방법이 매우 좋았던 것같아서 인상에 남는다.
여행지 탐색 목적에 맞게 보고 싶은 대륙 쪽으로 시점을 바꿀 수 있게 됐다. GSAP로 카메라 Y축 위치를 부드럽게 이동시키는 방식이었다.

### 10회 — UI 정리

```
rotation, view angle 옵션들을 우측 상단에 모아서 정리해줘.

"AI 세계 여행 다트"만 남기고 설명은 지워줘.
```

지구본이 훨씬 잘 보이게 됐다.

### 11회 — 마무리 수정 2가지

```
스테퍼 0.5가 아닌 0.1부터 2까지로 수정.
"지구본을 클릭하여 다트를 던지세요" 기본값에서 위치가 변하지 않도록 고정.
```

마지막으로 두 가지를 묶었다. 스테퍼 하한을 0.5에서 0.1로 낮춰서 거의 정지에 가까운 속도로도 조절 가능하게 했다. 힌트 텍스트가 정보 패널이 열릴 때 밀려나는 문제는 `position: absolute`로 화면 정중앙에 고정했다.

## 3. 효과적이었던 프롬프팅 전략

1. 구체적인 수치로 버그 리포트하기

    "좌표가 달라" 대신 "내가 찍은 곳은 -33.043154, 148.818657인데 앱에서는 -29.8653, 57.1677이 나와"처럼 실제 수치를 들고 갔다. 경도 차이가 91도라는 게 명확하게 드러났고, 단순 오프셋 문제가 아니라 축 방향이 잘못됐다는 걸 좁혀가는 데 도움이 됐다.

2. 직접 코드를 수정해서 요청하기

    Gemini가 내놓은 수정이 틀렸을 때, 직접 수정안을 써서 요청했다. AI에게 다시 생각해달라고 하는 것보다 내가 실험해서 찾은 답을 그대로 적용시키는 게 빨랐다. `atan2(-vec.z, vec.x)` 수정이 딱 그 경우였다.

3. 여러 독립 수정은 번호 붙여서 한 번에

    11회처럼 스테퍼 범위 수정과 힌트 텍스트 고정을 한 프롬프트에 묶었다. 각각 따로 날리면 컨텍스트가 끊기거나 앞 수정이 뒤에서 덮어씌워지는 경우가 생길 수 있다.

---

## 4. 배운 점

1. I가 원인 설명은 맞아도 수정이 틀릴 수 있다

    `Math.atan2` 버그가 정확히 그 경우였다. Gemini는 UV Mapping 오프셋이 문제라는 원인까지는 맞게 짚었다. 그런데 그 원인에서 도출한 수정 방향이 틀렸다. 이론과 실험이 따로 노는 영역이 있다는 뜻이다. AI가 설명을 잘 한다고 해서 수정도 잘 한다는 보장은 없다. 직접 실험해보는 게 답이었다.

2. 좌표 변환은 직접 축의 방향을 생각해야 한다

    Three.js의 좌표계, 텍스처 UV 매핑, 수학 함수 기준축이 전부 다 얽혀있었다. `atan2(y, x)`에서 어떤 벡터 성분이 y고 x인지, 부호가 어느 방향을 향하는지를 실제로 찍어가며 확인하지 않으면 이론으로만 맞추기 어려운 문제였다. 수학적으로 깔끔하게 설명되는 것처럼 보여도 실제 구현에서는 실험이 필요한 경우가 있다.

3. 페어 릴레이는 시점이 다양해진다

    혼자 하면 내가 신경 쓰이는 방향으로만 흘러간다. 번갈아 프롬프트를 쓰면 내가 생각하지 않았던 각도에서 기능이 붙기도 하고, 상대가 발견한 버그를 내가 수정하는 식으로 관찰 시점이 나뉜다. 같은 결과물을 두 사람이 번갈아 보면서 만드니까 놓치는 부분이 줄었다.
